# ETF Review OS — Repo File Classification

## Purpose

This file is the cleanup authority for the `daily-etf` repository.

Use it before deleting, archiving, renaming, or moving files. The goal is to keep the Weekly ETF Review operating system clean without breaking production delivery, bilingual rendering, pricing, state artifacts, or auditability.

## Safety rule

Do not delete a file only because its name looks old. First classify it by current usage:

1. Is it referenced by a production workflow?
2. Is it imported by an active Python module?
3. Is it listed as canonical in `control/SYSTEM_INDEX.md`?
4. Is it required for pricing, state, rendering, bilingual delivery, or validation?
5. Is it a generated artifact that supports auditability or historical continuity?

If any answer is yes, do not delete it without a replacement plan and validation run.

---

## Classification labels

### `ACTIVE_PRODUCTION`
Required for the current Weekly ETF Review production run or delivery path.

Delete policy: **never delete directly**. Only rename or refactor through a branch/PR with validation.

### `ACTIVE_SUPPORT`
Not always in the direct production send path, but still used for validation, state persistence, architecture control, split testing, or operational evidence.

Delete policy: **do not delete unless the related capability is explicitly retired**.

### `GENERATED_ARTIFACT`
Generated by reports, rendering, pricing, state persistence, or delivery.

Delete policy: **safe to prune selectively**, but preserve production reports, pricing audits, lane artifacts, and delivery receipts/manifests needed for auditability.

### `LEGACY_REVIEW`
Potential remainder from older work. May still contain useful context, but is not part of the active production path.

Delete policy: **review before deleting**. Prefer archiving first if uncertain.

### `DELETE_CANDIDATE`
Confirmed unused, reproducible, or obsolete.

Delete policy: **delete through a cleanup PR**, not directly on `main`.

## Cleanup process

### Phase 1 — classify before deleting
- Maintain this file.
- Update it whenever a file changes role.
- Do not delete files in this phase.

### Phase 2 — remove misleading active names safely
- Introduce a better-named replacement for active legacy-named files.
- Keep compatibility fallback for at least one production cycle.
- Validate render and delivery behavior before removing the old filename.

### Phase 3 — prune generated derivatives
- Remove or archive reproducible delivery derivatives.
- Preserve canonical markdown reports, pricing audits, lane artifacts, state artifacts, and delivery manifests.

### Phase 4 — remove confirmed legacy files
- Delete only files classified as `DELETE_CANDIDATE`.
- Use a cleanup PR and allow validation workflows to run.

## Current special notes

### `send_report_OLD.py`
This file is not currently safe to delete by name alone. It is still imported by `send_report.py` as the delivery base layer. The safer path is:

1. create a clearly named `delivery_base.py`
2. update `send_report.py` to import `delivery_base`
3. keep `send_report_OLD.py` temporarily as a compatibility fallback
4. after one successful production cycle, delete `send_report_OLD.py`

### `output_split_test/`
This folder is not production truth. It is retained only for split-test comparison and should not be used as source material for the live Weekly ETF Review unless explicitly requested.

### `prompts/as_is_split/`
This folder remains useful as an architecture workbench. It is not the live production runtime, but it should not be deleted while monolith-reduction remains an active direction.
